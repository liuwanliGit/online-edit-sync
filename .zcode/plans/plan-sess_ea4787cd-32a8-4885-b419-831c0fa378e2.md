# 计划：验证并修复协同 undo 的 Bug A（PM 改动不进 ydoc）

## 背景

已完成：Bug B 修复（协同模式直接调 Yjs UndoManager.undo()/redo()，绕过 extension-collaboration 坏掉的命令），并修了我自己的 PluginKey 重建 bug。现在 `undoManager` 能正确取出，按钮状态用事件驱动刷新。

剩余问题（Bug A）：用户输入后 `undoManager.undoStack` 永远为 0。实测诊断到：输入字符进了 PM（`pmHasInput=true`），但产生的 origin=`y-sync$` 本地事务**空转**（`beforeState==afterState`，`changedParentTypes.size=0`），字符没进 ydoc。

两份源码深度分析（y-tiptap 的 updateYFragment/mapping/view.update 门控 + Umo 全量事务分发排查）排除了 mapping 错位、Umo 拦截事务、localStorage 覆盖等假设，**把根因收缩到 y-tiptap 内部的 3 个可能点**。需要运行时打点确认是哪一个。

## 关键发现（来自源码分析）

1. **`updateYFragment` 不会因 mapping 缺失而空转**——mapping 没命中会回退到内容比较。空转的唯一条件是：传入的 PM doc 和 ydoc 在 `equalYTypePNode` 下完全一致。
2. **`view.update` 有门控**（y-tiptap.js:247-272）：只有 `initialContentChanged || findDiffStart(空默认doc) !== null` 时才进 `_prosemirrorChanged`。`initialContentChanged` 一旦置 true，**每次 update（含纯 selection 事务）都会进**——这解释了为什么有 6 条本地事务（多数是空转的 selection 事务）。
3. **预填空 paragraph 不是本次根因**：它只在 `fragment.length===0`（全新文档）时执行；测试时 ydoc 已有 19 个节点。
4. Umo 层没有任何代码拦截/改写 PM 事务分发（dispatchTransaction 是 Tiptap 原版）。

## 第一步：运行时打点验证（在 node_modules 打临时日志，不改 Umo 源码）

在 `node_modules/@tiptap/y-tiptap/dist/y-tiptap.js` 的 3 个位置打点（仅协同模式，靠 `window.__collabDebug` 标记区分），用浏览器实测输入 1 个字符，看 3 个位置的输出：

- **位置 A**：`view.update` 门控（line 238-272）——打印 `initialContentChanged`、`findDiffStart` 返回值、`view.state.doc` 的 textContent 前 40 字符、`isChangeOrigin`。确认输入事务是否进了 `_prosemirrorChanged`，还是被门控挡掉。
- **位置 B**：`_prosemirrorChanged` 入口（line 811）——打印传入的 `doc` 的 textContent，确认它是否包含刚输入的字符。如果**不包含**，说明传入的不是最新 PM doc（时序问题）。
- **位置 C**：`updateYFragment` 内部（line 1540 之后）——打印 `pNode.toJSON()` 摘要 vs `yDomFragment.toArray()` 摘要，特别是当 paragraph 被递归到时，看 yChildren 和 pChildren 各是什么。确认 `equalYTypePNode` 是否误判相等。

根据三处输出，根因会落到以下之一：
- **若 A 显示门控没通过** → 修复方向：调整门控条件或 `initialContentChanged` 置位时机。
- **若 B 显示传入 doc 没有新字符** → 时序竞争（远程 `_typeChanged` 整体重建覆盖了输入），修复方向：调整 sync 时机或 provider 配置。
- **若 C 显示 `equalYTypePNode` 误判相等** → y-tiptap 的 mark 处理 bug，修复方向：patch `equalYTypePNode` 或换比较逻辑。

## 第二步：根据根因实施针对性修复

打点确认根因后，**最小侵入**地修复。修复落在 Umo 源码（优先）或 y-tiptap 的 patch（不得已）：

- 若是门控问题 → 在 Umo 的 Collaboration 配置或 editor 初始化处补一个触发，确保 `initialContentChanged` 正确置位。
- 若是时序竞争 → 调整 HocuspocusProvider 的配置或 `editorReady` 的时机（app.vue 已有 `synced` 后挂载的逻辑，可能需要加延迟或额外事件）。
- 若是 y-tiptap 内部 bug → 在 `node_modules` patch（并记入 COLLAB_HANDOFF.md 的注意事项，标注重装会丢）。

## 第三步：端到端验证

修完后，浏览器实测完整流程：
1. 全新文档：输入字符 → undo 栈增长（按钮 enabled）→ 点 undo → 内容回滚 → 点 redo → 恢复
2. 已有内容文档（reload 后）：同上
3. 多窗口：A 输入 → B 看到同步 → A undo → B 看到 undo 生效（Yjs undo 是全局的，会回滚所有人的视图）
